# DevFest Hackathon 2026 提出用リポジトリ

  DevFest Hackathon 2026 のチームの **最終提出用** リポジトリです。提出期限までに、作品のコードと資料をこのリポジトリに置いてください。

  このリポジトリは **公開（public）** です。開催中も、運営・審査員・ほかの参加者が見られます。

## 作品：ShelfSight

視覚障害のある人がコンビニで買い物をするための Android アプリです。胸の前にスマホを立てて持ち、イヤホンで聞きます。

| 操作 | すること |
|---|---|
| 長押し | 「調べています」と言い、手前の商品 1 つなら社名と商品名（③）、棚の広い範囲なら並んでいる商品の説明（②）、その間なら「一歩下がって」と頼む |
| 2 回たたく | 質問する。「何がある？」「これは何？」「止めて」「もう一度」などはその操作、それ以外は LLM が今のカメラの画像を見て答える |

TalkBack が有効なときは、ダブルタップが質問、ダブルタップ長押しが長押しです。

人の検出では、自分の手や持っている商品を人と間違えないよう、画面の下からだけ入ってくる枠、手の届く距離なのに画面の上まで写っていない枠、全身に見えるのに縦に長くない枠を外します（`PersonFilter`、手の検出は使わない）。

### iOS 版

`ios/` に、買い物の案内（下の `assist`）を同じ構成で Swift に移した iOS 版があります（ARKit・Vision・AVFoundation・ONNX Runtime）。モデルと照合先は Android 版と同じファイルを使います。ビルドは GitHub Actions（`.github/workflows/ios-testflight.yml`）から TestFlight に上げます。準備は [ios/README.md](ios/README.md) を見てください。iOS 版と Android 版は、いつも機能を同じにします（片方を変えたら、もう片方も同じように変える）。

### 買い物の案内（`assist` パッケージ、起動すると開く画面）

| 場面 | すること | 使うもの |
|---|---|---|
| ① 棚が複数写っている | **止めている**（歩行中の判別の 8 列 × 7 分類は遅いので動かさない。「何の棚？」と聞かれたら、画像を見て LLM が答える） | - |
| ② 棚が 1 つ写っている（長押し、または自動） | 商品を認識し、LLM（Gemini、lite モデルを先に使う）で「うえのほうには緑茶や麦茶、したのほうにはジュースが並んでいます」のような短い自然な文にして話す。**場違いな商品は LLM に渡す前に外す**（7 分類と細分類のそれぞれで、棚の中で 25% に満たないものを外す。パン棚のチョコ菓子も、ポテトチップスの棚のグミも外れる）。名前を付ける切り抜きは大きいものから 40 個まで | 商品認識ダッシュボード（`products/`）の YOLO・埋め込み・照合先、周りの商品による補正（`ContextAdjust`）、少数ジャンルの除外（`ShelfDescriber`）、`Narrator` |
| ③ 商品が 1 つ大きく写っている（長押し） | Cloud Vision API（Web 検索・ロゴ・文字）で調べて社名と商品名を言う。1 回の接近につき API は 1 回だけ呼ぶ | `ProductLookup`、`VisionProductParser` |
| ④ 人が近づいてくる | その人の方向からピコピコ鳴らす（近いほど速く） | MediaPipe の人検出、`PersonTracker` |

- 1 秒ごとに、カメラの画像・ARCore の姿勢と向き・商品認識の結果を `Android/data/jp.devfest.shelfsight/files/records/<起動時刻>/`（画像と `records.jsonl`）に記録します（`Recorder`）。認識した商品は、深度と ARCore の縦の平面（壁）から位置を決めて、AR 空間の地図に貯めます（`ShelfMap`、アプリを閉じると消える）。長押しで棚を説明するときは、今見えている商品を地図から取り出し、同じ場所で何度も見えた名前を使います（1 枚ごとの読み違いに強い）
- 名前を付ける切り抜きは、1 枚につき大きいものから 20 個まで
- 写っているものは `SceneJudge` が決めます（2 回続けて同じ判定になったら切り替え）
- 立体音響は `SpatialMixer` / `Binaural`（左右の時間差・音量差・頭の陰、後ろはこもらせる）。ARCore の向きで毎ブロック計算し直すので、スマホを回しても音は店の中の同じ場所にとどまります
- 声は端末の音声合成（日本語）、聞き取りは端末の音声認識です。「上段」を「じょうだん」と読むような読み間違いを避けるため、位置の言葉はひらがなにしてから読みます（`Reading`）
- 商品認識の検出の精度は val mAP50 0.62

#### 準備

1. リポジトリ直下の `.env`（または `local.properties`）に `GCP_API_KEY=...`（Cloud Vision）と `GEMINI_API_KEY=...`（説明と質問）を書く。キーは APK に入るので、ビルドした APK を人に渡さないこと。Vision がなければ ③、Gemini がなければ質問が使えず、② は決まった言い方の文になります
2. 歩行中の判別の画像エンコーダを書き出す（重みが Apple の研究用ライセンスなのでリポジトリに含めていない）: `tools/coarse_export_encoder.py` の説明どおりに環境を作り、`python tools/coarse_export_encoder.py MobileCLIP2-S0`。`app/src/main/assets/coarse/MobileCLIP2-S0.onnx` ができる。なければ ① だけ使えません
3. 商品認識のモデルを書き出す（商品認識ダッシュボードで学習し直したとき）: `python tools/export_products.py --work products/work`
4. `./gradlew :app:installDebug`（JDK 17 以上）。カメラとマイクを許可します

地図づくり（下記）と Store3D の画面は開発用として残してあり、ランチャーには出ません。

### 地図づくり（開発用）

店内を歩くと ARCore で自分の位置と店全体の 3D 地図を作ります。作った地図は端末の画面で確認できます。

### 処理の流れ

1. `StoreMapper`：ARCore から自己位置と生深度を取得し、約 2.5m 単位の区画に分ける
2. `DepthFusion` / `VoxelGrid`：深度を 3D の点に戻し、5cm 単位で統合する（2 回以上観測された点だけを地図に残す）
3. `SurfaceMap`：ARCore の平面検出の結果を、床・棚などの上面・壁の面として持つ（天井は除く）
4. `SurfaceFitter` / `SurfaceFusion`：深度の点を手がかりに面を補正する。同じ平面をまとめ、つながっている点の範囲まで広げ、ARCore が見落とした平面を点から見つける。遠くの壁には、密な深度を 10m まで集めた手がかりを使う（誤差が大きいので床には使わず、面として認める条件も厳しくする）
5. `MapRenderer` / `SurfaceRenderer`：面、歩いた軌跡、現在地を描画する。点群は「点も重ねて表示」で重ねられる

各区画は ARCore の Anchor に結びつけているため、歩行中に ARCore が位置を補正しても区画ごと追従します。面は ARCore の平面そのものなので、同じ補正が反映されます。

### 人と壁の判別

胸に固定したカメラで、正面にあるものを判定して画面に表示します。

1. `MediaPipePersonDetector`：カメラ画像から人を検出する
2. `PersonDistance` / `PersonTracker`：人の距離と 3D 位置を求め、位置の変化から「止まっている」「向かってくる」などを判定する
3. `ObstacleClassifier`：人以外の正面の深度を 3D の点に戻し、縦の平面に並ぶなら壁、それ以外なら物とする。データが足りないときは「確認できません」と表示する

検出した人は 3D 地図の上に、動きごとに色分けした柱としてリアルタイムの位置で表示します。距離が分からない人は地図に置けないので、人数だけを表示します。

### 手と指の認識

`MediaPipeHandDetector` で手の 21 点を読み取り、`HandAnalysis` で左右、形（指さしなど）、指の向き、手のひらの向き、距離、指先のワールド座標を求めます。人として検出された枠が手で大きく占められている場合は、`OwnHandFilter` で自分の手や腕の誤認として除外します。

### 棚と商品の判別

| 場面 | 処理 | 処理する場所 |
|---|---|---|
| 歩いている（0.5 秒以上の間隔で、前の判別が終わりしだい） | 画面を 8 列に分け、列ごとの大まかなカテゴリ（6 分類＋商品なし。`tools/coarse_categories.json`） | 端末（MobileCLIP ＋ ONNX Runtime） |
| 棚の前で立ち止まる（`DwellDetector`：1.5 秒） | 列ごとのカテゴリ（`labels.txt` の 26 分類） | クラウド（Gemini） |
| 商品を手に取る（`SceneChangeDetector` / `HeldProductDetector`：0.8 秒） | OCR で商品名を読み取る（Cloud Vision API。キーがない・通信できないときは ML Kit） | クラウド（予備は端末） |

- 商品の画像は、Cloud Vision の API キーを設定したときだけ Google に送ります（`local.properties` に `CLOUD_VISION_API_KEY=...` か `GCP_API_KEY=...`）。Vision API の同期の要求では、画像はメモリ上で処理され、保存も学習への利用もされません。読み取りは、箱で手が隠れても、視界がふさがれて AR の追跡が切れても動きます。文字を読めないときは撮り直し、それでも読めなければ読めないと伝えます
- `RequestBudget` で、クラウドの呼び出しを 1 分あたり 12 回までに制限しています
- 棚の判別を使うには `local.properties` に `GEMINI_API_KEY=...` を書きます（任意で `GEMINI_MODELS=a,b,c`。混雑していると次のモデルに切り替えます）。キーがなければ棚の判別だけが止まります
- 歩行中の判別のモデルは大きく、重みが Apple の研究用ライセンス（apple-amlr）なのでリポジトリに含めていません。`tools/coarse_experiment.py --export-head 3` で作った `app/src/main/assets/coarse/<名前>.onnx` と `<名前>.head.json` を置き、`local.properties` の `COARSE_MODEL`（既定は `MobileCLIP-S1`）で選びます。置いていなければ歩行中の判別だけが止まります。デバッグ版は結果と時間を `walking_log.tsv` に残します
- 指示文とスキーマは `app/src/main/assets/cloud/` にあり、`tools/cloud_test.py` で同じものを写真で試して、入出力の一覧を `tools/out/cloud_test/report.html` に出せます

### 使用技術

- ARCore（位置追跡、Depth API）、OpenGL ES
- MediaPipe Object Detector（EfficientDet-Lite0）、Hand Landmarker（いずれも端末内で実行）
- Kotlin / Jetpack Compose

商品の判別（Gemma 4 / LiteRT-LM）のコードは `vision` パッケージなどにありますが、今は使っていません。地図へのラベル付けを実装するときに接続します。

### 動かし方

ARCore と Depth API に対応した実機が必要です。

```
./gradlew :app:installDebug
```

起動して端末を左右に動かすと記録が始まります。店内を歩いたあと「地図を見る」を押すと、1 本指で回転、2 本指で移動と拡大ができます。地図はまだ保存されず、アプリを終了すると消えます。

  ## 開発用のリポジトリは別に作ることをおすすめします

  このリポジトリでは **GitHub Actions と GitHub Pages が使えません**。CI やデプロイ、Pages での公開をしたいときは、チームで開発用のリポジトリを別に作ってください。

  - 開発用のリポジトリは、チームのメンバーのアカウントや、チームで作った Organization に作ってください
  - 開発はそちらで進めて、提出期限までに最終版のコードと資料をこのリポジトリに push してください
  - 審査はこのリポジトリの内容で行います。開発用のリポジトリにしかないものは、審査の対象になりません
  - デプロイした作品の URL があれば、この README に書いてください

  ## 秘密情報をコミットしない

  API キー・パスワード・サービスアカウントの鍵などは、**絶対にコミットしないでください**。公開リポジトリなので、push
  した時点で誰でも見られます。開発用のリポジトリから持ってくるときも、履歴ごと push すると、過去のコミットに含まれる秘密情報も公開されます。

  - 秘密情報は `.env` や `.dev.vars` などに書き、コミットしない（`.gitignore` に入れてあります）
  - 誤って push したら、すぐにキー（鍵）を無効にして作り直し、運営に連絡してください。履歴から消すだけでは不十分です
  - GitHub の push protection が、よく知られた形式のキーの push を止めることがあります。止められたら、そのキーをコミットから外してください
